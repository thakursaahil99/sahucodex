# API reference

The API is generated by FastAPI, so the authoritative, always-current reference is the interactive OpenAPI page at
**`/api/docs`** (raw schema: `/api/openapi.json`). This page documents the conventions.

* Base path: `/api`. JSON in, JSON out.
* Authenticate with `Authorization: Bearer <access_token>` (see [authentication.md](authentication.md)).
* Every response carries `X-Request-ID`; quote it when reporting a problem. You may send your own (8–64 chars of
  `A–Z a–z 0–9 . _ -`), otherwise one is generated.

## Error format

Every error — validation, authentication, rate limiting, unexpected failures — uses one envelope:

```json
{
  "success": false,
  "error": {
    "code": "SUBMISSION_NOT_FOUND",
    "message": "Submission not found",
    "details": [ { "field": "email", "message": "value is not a valid email address", "type": "value_error" } ]
  }
}
```

`code` is stable and machine-readable; `message` is for humans; `details` appears only for `VALIDATION_ERROR`. Validation
details never echo the submitted value (it might be a password). Unhandled exceptions return
`{"code": "INTERNAL_ERROR", "message": "An unexpected error occurred"}` — no stack traces, ever — and are logged
server-side with the request id.

| Status | Codes |
|---|---|
| 400 | `TOKEN_INVALID` (bad/expired emailed link) |
| 401 | `NOT_AUTHENTICATED`, `TOKEN_EXPIRED`, `TOKEN_INVALID`, `TOKEN_REVOKED`, `ACCOUNT_UNAVAILABLE`, `INVALID_CREDENTIALS`, `REFRESH_TOKEN_MISSING`, `REFRESH_TOKEN_INVALID`, `REFRESH_TOKEN_EXPIRED`, `REFRESH_TOKEN_RACE`, `REFRESH_TOKEN_REUSED` |
| 403 | `FORBIDDEN`, `ACCOUNT_DISABLED`, `CSRF_ORIGIN_MISMATCH` |
| 404 | `NOT_FOUND`, `USER_NOT_FOUND`, `SESSION_NOT_FOUND`, `PROBLEM_NOT_FOUND`, `HINT_NOT_FOUND`, `SUBMISSION_NOT_FOUND`, `RUN_NOT_FOUND` |
| 405 / 413 | `METHOD_NOT_ALLOWED`, `PAYLOAD_TOO_LARGE` |
| 409 | `EMAIL_TAKEN`, `USERNAME_TAKEN`, `ACCOUNT_EXISTS`, `SLUG_TAKEN`, `TAG_EXISTS`, `PROBLEM_ARCHIVED`, `PROBLEM_NOT_JUDGEABLE` |
| 422 | `VALIDATION_ERROR`, `PROBLEM_NOT_READY`, `UNKNOWN_TAG`, `UNKNOWN_LANGUAGE`, `UNKNOWN_TEST_CASE`, `INVALID_TAG`, `LANGUAGE_DISABLED`, `SOURCE_TOO_LARGE`, `INVALID_SOURCE`, `INPUT_TOO_LARGE`, `INVALID_INPUT`, `NO_SAMPLES` |
| 429 | `RATE_LIMITED`, `TOO_MANY_PENDING_SUBMISSIONS` — both include a `Retry-After` header (seconds) |
| 500 / 503 | `INTERNAL_ERROR`, `SERVICE_UNAVAILABLE`, `JUDGE_UNAVAILABLE` |

## Pagination

List endpoints take `?page=1&limit=20` (`limit` ≤ 100) and return:

```json
{ "items": [ … ], "total": 123, "page": 1, "limit": 20, "pages": 7 }
```

Offset pagination is used for admin and moderate-size lists, including submission history (`GET /api/users/me/submissions`)
— a per-user list, so even a heavy user's history stays small enough that offset pagination's cost is negligible.
High-churn, cross-user lists added later (notifications, contest leaderboards) will use cursor pagination instead, to
keep deep pages cheap.

## Endpoints implemented so far

| Method & path | Auth | Purpose |
|---|---|---|
| `POST /api/auth/register` | – | Create an account (does not sign in) |
| `POST /api/auth/login` | – | Sign in by email or username; sets the refresh cookie |
| `POST /api/auth/refresh` | cookie | Rotate the refresh token, return a new access token |
| `POST /api/auth/logout` | cookie | Revoke the session (idempotent) |
| `GET /api/auth/sessions` | user | List my active sessions |
| `DELETE /api/auth/sessions/{id}` | user | Sign one of my sessions out |
| `POST /api/auth/verify-email/request` | user | Send a new verification link |
| `POST /api/auth/verify-email` | – | Confirm an email with a token |
| `POST /api/auth/password/forgot` | – | Request a reset link (always `202`) |
| `POST /api/auth/password/reset` | – | Choose a new password with a token |
| `GET /api/users/me` | user | My account and profile |
| `PATCH /api/users/me` | user | Update bio, country, website, GitHub URL, avatar URL |
| `GET /api/users/{username}` | – | Public profile (no email, no roles) |
| `GET /api/users/{username}/stats` | – | Solved counts by difficulty, submission totals and acceptance rate, streak, achievements (earned and locked), a 365-day activity calendar — see [database.md](database.md#phase-4-schema-migration-0004) |
| `GET /api/admin/users` | **ADMIN** | Paginated user list; `?q=` searches username/email |
| `GET /api/problems` | – (personalised if signed in) | Search, filter and sort published problems; see [problems.md](problems.md#finding-problems) |
| `GET /api/problems/{slug}` | – | Statement, examples, starter code. Editorial only for solvers and admins. Never hidden tests |
| `GET /api/problems/{slug}/hints/{n}` | – | Reveal hint `n` (1-based) |
| `GET /api/tags`, `GET /api/languages` | – | Topics (with problem counts) and supported languages |
| `GET/POST /api/admin/problems` | **ADMIN** | List (incl. drafts and archived; `?status=`, `?q=`) / create a draft |
| `GET/PUT /api/admin/problems/{id}` | **ADMIN** | Full problem *including hidden tests* / replace it (test cases synced by id) |
| `GET /api/admin/problems/{id}/validation` | **ADMIN** | Dry run of the publish checks |
| `POST /api/admin/problems/{id}/{publish,unpublish,archive,restore}` | **ADMIN** | State changes; `publish` returns `422 PROBLEM_NOT_READY` listing the blockers |
| `POST /api/admin/tags` | **ADMIN** | Create a tag |
| `POST /api/submissions` | user | Judge a solution; returns `{id, status}` immediately (`202`), the worker does the work — see [judge.md](judge.md) |
| `GET /api/submissions/{id}` | user (owner only) | Verdict, runtime, memory, compiler output and *public* test results — never hidden tests |
| `GET /api/users/me/submissions` | user | My submission history; `?problem=`, `?verdict=`, `?language=`, `?status=` |
| `POST /api/run` | user | Run against the problem's examples (`mode=samples`) or custom input (`mode=custom`); returns `{id}` (`202`) |
| `GET /api/run/{id}` | user (owner only) | The run's status and result; expires after `RUN_RESULT_TTL` |
| `POST /api/ws/ticket` | user | A single-use, 30-second ticket for the event socket (browsers cannot set an `Authorization` header on a WebSocket) |
| `GET /api/ws?ticket=…` (WebSocket, root path — not under `/api`'s HTTP middleware) | ticket | `submission.queued/running/completed/failed`, `run.running/completed/failed` for the ticket's own user only |

Operational endpoints (root, not `/api`, not reachable through the proxy): `GET /health` (liveness), `GET /ready`
(PostgreSQL + Redis; `503` with per-dependency `ok`/`unavailable` and no internals), `GET /metrics` (Prometheus, optional
`METRICS_TOKEN` bearer).

Further endpoints (`/api/contests`, `/api/ai/*`, `/api/leaderboard`, `/api/notifications`) arrive with their phases,
following the paths in the project specification.

## Limits

Request bodies are capped at `MAX_REQUEST_BYTES` (default 1 MiB): oversized requests get `413`, including chunked
uploads that declare no `Content-Length`. `/api/admin/*` requests that carry a bearer token may send up to
`ADMIN_MAX_REQUEST_BYTES` (8 MiB), for large hidden test files. Rate limits are listed in [authentication.md](authentication.md#rate-limits-defaults-all-configurable).
